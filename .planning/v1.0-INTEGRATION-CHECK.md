## Check 1: metadata.json Schema — Phase 1 Writer vs Phase 3 Reader

**Verdict: WIRED**

`buildMetadata()` in `src/lib/metadata.ts` produces the `Metadata` interface from `src/types.ts`:
```
id, original_filename, mime_type, size_bytes, sha256, created_at, label,
source_ip, tsa_provider, tsa_status ("verified"), tsa_attested_at, tsa_fallback_chain (TsaProvider[])
```

The Phase 3 `ArchiveDetailMeta` interface in `src/views/archive-detail.ts` (post-commit f0e650f) reads:
```
id, original_filename, mime_type, size_bytes, sha256, created_at, label,
source_ip, tsa_provider, tsa_status, tsa_attested_at, tsa_fallback_chain (string[])
```

**Field-name fix verified:** Commit f0e650f renamed `submitter_label` → `label` and `server_timestamp` → `created_at` in `ArchiveDetailMeta`. No occurrences of obsolete names remain in `src/` (grep confirms).

**Remaining type gap (WARNING):** In `src/routes/archive.ts:128`, the route reads `metadata.json` as `Record<string, unknown>` and casts it via `meta as unknown as ArchiveDetailMeta`. This is an unsafe cast — no runtime validation. In practice it is safe because the file was written by `buildMetadata()` with a guaranteed schema, but a corrupted or hand-edited `metadata.json` with missing fields would cause silent undefined rendering rather than an error. No BLOCKER since there is no code path that produces non-conforming metadata.json files under normal operation.

**tsa_fallback_chain type mismatch (WARNING):**
- In `ArchiveDetailEntry` (from DB row): `tsa_fallback_chain: string` (JSON-encoded)
- In `ArchiveDetailMeta` (from metadata.json): `tsa_fallback_chain: string[]` (parsed array)
- The view (`archive-detail.ts`) does NOT render `tsa_fallback_chain` anywhere — it is declared in the interface but never used in the template. No functional impact, but the types represent different shapes for the same conceptual field. If a future implementer adds fallback chain rendering they will encounter this asymmetry.

### Warnings (Non-Blocking)

**W1 — Unsafe metadata.json type cast in archive route**
- File: `src/routes/archive.ts:128`
- Issue: `meta as unknown as Parameters<typeof renderArchiveDetailPage>[0]["meta"]` casts `Record<string,unknown>` without runtime field validation
- Risk: Silent empty-string rendering if a bundle's metadata.json is hand-edited or partially corrupted
- Impact: No user-facing data integrity break on bundles written by the server; only affects manually corrupted bundles
- Affected REQ: BROWSE-02

**W2 — tsa_fallback_chain type asymmetry across interfaces**
- `ArchiveDetailEntry.tsa_fallback_chain: string` (DB TEXT, JSON-encoded)
- `ArchiveDetailMeta.tsa_fallback_chain: string[]` (metadata.json, native array)
- Neither is rendered in the view template — declared in interface but unused
- If a future implementer adds fallback chain display they will encounter a type confusion bug
- Affected REQ: BROWSE-02 (future risk)

**W3 — GET /archive list-page DB-failure returns JSON envelope instead of HTML**
- File: `src/routes/archive.ts:74-79`
- The catch block returns `errorResponse()` (JSON `{error:true, ...}`) for a page route
- The UI-SPEC §Error States implies a red HTML banner should be shown
- A logged-in user whose SQLite query throws will see raw JSON in the browser
- This was noted as an INFO deviation in the Phase 3 VERIFICATION.md
- Affected REQ: BROWSE-01

**W4 — REQUIREMENTS.md traceability table shows Phase 2 requirements as "Pending"**
- File: `.planning/REQUIREMENTS.md:84-89`
- UPLOAD-01, UPLOAD-02, UPLOAD-03, SEC-01, SEC-02, LEGAL-01 all show `Status: Pending`
- All six are fully implemented and verified (Phase 2 VERIFICATION.md: passed 5/5)
- This is a documentation staleness issue only — the code is correct
- Affected REQ: UPLOAD-01, UPLOAD-02, UPLOAD-03, SEC-01, SEC-02, LEGAL-01
