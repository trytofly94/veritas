## Phase Goal

**As a** archive owner (Lennart), **I want to** click any row in the archive list and see every metadata field for that entry — plus re-verify its SHA-256 integrity with one click — **so that** I can confirm exactly what was archived, when, by which TSA, and that the file on disk is still unaltered, all without leaving the browser.

<objective>
Deliver the second end-to-end vertical slice of the archive browser: the detail page at `/archive/:id` showing every metadata field from `metadata.json`, the TSA status badge, a download-bundle action, and an interactive "Integrität jetzt prüfen" component (Alpine.js) backed by a new auth-gated `POST /api/archive/:id/verify` endpoint that re-hashes the on-disk original file and compares to the stored SHA-256.

Purpose: Closes BROWSE-02 — the owner can inspect every metadata field of an archived entry and confirm its integrity from the browser.
Output: New view module + 404 view, two new pure formatters, new integrity-verify library function, new Alpine component, two new routes registered on the existing `registerArchive` registrar, full unit + e2e test coverage.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → GET /archive/:id | Untrusted client requests authenticated detail page. Session cookie is auth. URL path param is user input. |
| Browser → POST /api/archive/:id/verify | Untrusted client triggers server-side filesystem read + hash. Auth via session. |
| Server → filesystem (bundleDir/original.<ext>) | Path constructed from DB row (server-trusted), not from URL — but the URL ID maps to the row. |
| Server-rendered HTML → browser DOM | metadata.json fields (submitter_label, original_filename, source_ip) are user-controlled at upload time. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-08 | Spoofing | GET /archive/:id auth | mitigate | `requireSessionPage(deps)` enforced; invalid/missing cookie → 303 to `/login?next=...`. Verified by e2e test 1 in archive-detail.test.ts. |
| T-03-09 | Spoofing | POST /api/archive/:id/verify auth | mitigate | `requireSessionApi(deps)` enforced; missing cookie → 401 UNAUTHORIZED envelope (NOT a redirect — this is an API endpoint). Verified by e2e test 1 in archive-verify.test.ts. |
| T-03-10 | Tampering | Path traversal via :id parameter | mitigate | ULID regex `/^[0-9A-HJKMNP-TV-Z]{26}$/` applied BEFORE any DB lookup or filesystem access. Anything failing the regex returns 404 immediately. `bundle_dir` is read from DB row, not constructed from URL. Verified by e2e invalid-ULID tests. |
| T-03-11 | Tampering | Path traversal via metadata.original_filename when computing `original.<ext>` | mitigate | We compute `path.extname(originalFilename)` which strips everything before the last `.`. An adversarial filename like `../../etc/passwd.txt` yields ext `.txt`; we join `path.join(bundleDir, "original.txt")` which stays inside bundleDir. Note: bundle_dir itself is server-controlled (set by upload pipeline), not user-controlled. |
| T-03-12 | Information disclosure | XSS via metadata fields (submitter_label, original_filename, source_ip) in detail HTML | mitigate | `escapeHtml()` applied to every interpolated user-provided value in `renderArchiveDetailPage`. Verified by Task 2 unit test with `<img onerror=...>` payload. |
| T-03-13 | Information disclosure | Error message leaks file paths | mitigate | `errorResponse(c, 500, "INTERNAL_ERROR", "Unbekannter Fehler.")` returns generic German message; full path + error logged via `console.error` only. Inherits Phase 2 pattern. |
| T-03-14 | Denial of service | Large-file streaming hash on every verify click | accept | Bounded by Phase 2's 100 MB upload cap; SHA-256 streaming on a 100 MB file completes in <2s on Unraid hardware. v1 trust assumption: only authenticated single-tenant family use. |
| T-03-15 | Repudiation | Verify result is not logged | accept | v1: no audit trail required; the bundle ZIP itself is the legal evidence. Future: structured log line. |

| T-03-17 | Information disclosure | TimingSafeEqual on hash comparison leaks hash via timing | accept | The hash comparison is server-internal (no attacker-controlled input to the comparison — both sides come from server-trusted sources). `timingSafeEqual` is used as defense-in-depth, not for a security-critical comparison. |
| T-03-18 | Tampering | Race condition: file is replaced between row read and stream hash | accept | v1: single-writer pipeline (uploads are sequential through Hono). Concurrent tampering would require filesystem access to the data volume, which is already game-over. |
