<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Node service → second/third TSA | Same TLS/cert-validation boundary as DFN; FreeTSA over HTTPS, DigiCert over HTTP (no TLS) — TSR is signed end-to-end so TLS is defense-in-depth only |
| verify.sh → bundle filesystem | verify.sh runs on third-party hosts with unknown openssl versions; must avoid bashisms and assume `/bin/sh` (dash on Debian) |
| Service → env var TSA endpoints | TSA_*_ENDPOINT overrides could be abused by attacker with env access to redirect TSA traffic to attacker-controlled server, then forge signature — mitigated because pre-finalization verify checks signature against the COMMITTED CA cert (not a fetched one) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | TSR replaced in transit or by hostile TSA endpoint | mitigate | `verifyTsr` runs `openssl ts -verify` with the **committed** CA cert (assets/tsa-certs/&lt;provider&gt;.pem) BEFORE the bundle is written. A forged TSR fails signature verification and the provider is skipped. |
| T-02-02 | Tampering | CA cert swapped at runtime via env var or filesystem | accept (Phase 1) | CA certs are committed into the image (Plan 03 bakes them in). At runtime the path is relative to the working dir; no env override exists. Phase 2+ may add a `--trusted-cert-bundle` flag. |
| T-02-03 | DoS | All three TSAs slow → request hangs | mitigate | Per-provider AbortController timeout of 10s (CONTEXT Discretion budget); worst case 30s for the full chain. Documented in code comment near the timeout constant. |
| T-02-04 | Repudiation | metadata.json claims tsa_provider that does not match the actual signer | mitigate | tsa_provider is set from the provider whose verifyTsr **succeeded**; CA cert copied into bundle is that same provider's cert; verify.sh re-checks both at any later time. |
| T-02-05 | Elevation of privilege | verify.sh interpreted by a maliciously crafted /bin/sh | accept | Out of scope — user runs verify.sh on their own machine; they trust their own shell. |
| T-02-06 | Information disclosure | verify.sh embeds absolute paths from the build host | mitigate | verify.sh uses only `$(dirname "$0")`-relative paths; grep gate in acceptance_criteria asserts no `/Users/` `/home/` `/tmp/` substrings in non-comment lines. |
| T-02-07 | DoS | Repeated upload attempts during TSA outage flood logs / disk | accept (Phase 1) | Phase 1 has no auth so attacker has unbounded calls anyway; rate-limit + auth land in Phase 2. D-05 ensures failed attempts cost nothing on disk. |
</threat_model>
