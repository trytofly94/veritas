<objective>
Walking Skeleton — Wave 1 of Phase 1. Stand up the thinnest possible end-to-end vertical slice: a `POST /api/upload` Hono endpoint that hashes the uploaded file, obtains an RFC 3161 timestamp from DFN-TSA (single provider, no fallback yet), and writes a complete bundle directory to disk. This plan proves the entire stack (TS + Hono + multipart + OpenSSL subprocess + outbound HTTPS to a real TSA + atomic filesystem write) works on the developer host. Fallback chain, verify.sh, and Docker arrive in subsequent plans.

Purpose: De-risk the cryptographic + TSA integration path before adding Docker, fallback complexity, or polish. After this plan, a real user can submit a file via curl and get back a verifiable bundle on disk — something they could not do before.

Output: A runnable `npm run dev` server with a working happy-path upload that produces a real DFN-signed bundle, plus a failing-first E2E test that locks the behavior in.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP client → /api/upload | Untrusted multipart bytes, untrusted filename, untrusted label, untrusted X-Forwarded-For header |
| Node service → OpenSSL subprocess | Subprocess arguments must not include attacker-controlled strings as flags |
| Node service → DFN-TSA endpoint | External network; response is an unauthenticated binary blob until OpenSSL parses + signs validate |
| Node service → host filesystem (DATA_DIR) | Bundle directory names + filenames must never escape DATA_DIR |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Tampering | Uploaded filename used as on-disk path | mitigate | Bundle filename is always `original<ext>` where `ext = path.extname(uploaded)`; uploaded filename is stored only inside metadata.json. Directory name is server-generated ULID — never derived from user input. Path traversal in `ext` impossible because `path.extname` returns only the trailing `.xxx` segment. |
| T-01-02 | DoS | Unbounded multipart upload exhausts memory/disk | mitigate | Hono `bodyLimit` middleware set to 100 MiB on /api/upload (matches Phase 2 Cloudflare limit; documented in code comment). Reject larger requests with 413 before reading the body. |
| T-01-03 | Information disclosure | TSA endpoint over plaintext HTTP | mitigate | DFN endpoint reached over `https://zeitstempel.dfn.de` (TLS). Node's default fetch validates certs; do NOT disable TLS verification. CA cert for verifying TSR signatures is committed under `assets/tsa-certs/dfn.pem`, not fetched at runtime. |
| T-01-04 | Tampering | TSA response substitution / man-in-the-middle | mitigate | `openssl ts -verify` is invoked in Plan 02 against every TSR using the bundled CA cert; Plan 01-01 does not write to disk before successful TSA round-trip but does not yet run `-verify` (deferred to Plan 02 — explicit). Pre-finalization verify is added in Plan 02 (D-09 chain). |
| T-01-05 | Tampering | Concurrent uploads racing on the same bundle directory | mitigate | Each bundle uses server-generated ULID; collision probability negligible. Write happens in `DATA_DIR/.tmp-<ulid>` then `fs.rename` to `DATA_DIR/<ulid>` — atomic on same filesystem. |
| T-01-06 | Repudiation | Source IP spoofing via X-Forwarded-For | accept | Phase 1 has no auth and runs behind no proxy; source_ip is best-effort. Phase 2 introduces auth + Cloudflare Tunnel; X-Forwarded-For only honored when the front proxy is in place. Documented in D-14 and metadata.json field semantics. |
| T-01-07 | Elevation of privilege | OpenSSL invoked with shell injection | mitigate | Always use `child_process.execFile('openssl', [...args])` — never `exec` or string concatenation. The only attacker-controlled value reaching openssl is the SHA-256 hex digest, which is validated to `/^[0-9a-f]{64}$/` before being passed as a `-digest` argument. |
| T-01-08 | Information disclosure | Container/process runs as root | accept (Phase 01-01) | Plan 01-01 runs on the developer host. Container hardening (non-root user, read-only rootfs) is owned by Plan 03 where Docker is introduced. |
</threat_model>
